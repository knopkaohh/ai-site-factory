# Архитектура AI Site Factory

## Спринт 1

Монорепозиторий из трёх частей:

- `shared` — контракт, который одинаково проверяют панель и API: режимы, статусы, этапы, нормализация домена и разбор входных данных.
- `backend` — Express и SQLite. Бизнес-операции проекта находятся в `services`, SQL — в `repositories`.
- `frontend` — React + Vite. Страницы вызывают `/api` и не хранят проекты локально.

Такое разделение достаточно для одного процесса API и статической панели. Отдельные сервисы и брокер очередей на этом этапе только усложнили бы запуск.

## Модель данных

`projects`

- идентификатор UUID;
- название, домен, ТЗ, необязательные требования;
- режим `autopilot` или `stage_approval`;
- статус, текущий этап и прогресс 0–100;
- даты создания и обновления;
- `name_folded` для поиска без учёта регистра, включая кириллицу.

Статусы проекта: `created`, `in_progress`, `awaiting_review`, `demo_ready`, `published`, `error`.

`project_stages` ссылается на проект с `ON DELETE CASCADE`. У этапа есть ключ, название, позиция, статус, время начала и завершения, текст ошибки. Допустимые статусы этапа: `pending`, `in_progress`, `awaiting_review`, `completed`, `error`.

Начальные этапы, все в статусе `pending`:

1. `collect` — Сбор исходного сайта
2. `analyze` — Анализ и паспорт сайта
3. `concept` — Концепция редизайна
4. `develop` — Разработка нового сайта
5. `qa` — Тестирование и исправление ошибок
6. `demo` — Подготовка демоверсии
7. `publish` — Публикация

Прогресс считается только по этапам в статусе `completed`. Текущий этап — первый не завершённый. При создании это даёт прогресс 0 и этап `collect`.

`project_events` хранит историю. Сейчас пишутся `project.created` и `project.updated`. Создание проекта, его этапов и первой записи истории выполняется в одной транзакции.

Даты — строки ISO 8601 с суффиксом `Z`.

Домен сохраняется без протокола, порта, пути и запроса, в нижнем регистре. Кириллический домен остаётся в Unicode. IP-адреса, localhost, логин в адресе и протоколы кроме http/https отклоняются. Исходный сайт при этом не запрашивается.

## API

Ответы с данными: `{ "data": ... }`.

Ошибки: `{ "error": { "code", "message", "details"? } }`. `details` — список `{ "field", "message" }`. Неизвестный проект и неверный идентификатор дают 404.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/health` | версия, время проверки, SQLite и список интеграций. 200, если база отвечает, иначе 503 и `status: degraded` |
| GET | `/api/projects` | список и сводка. `q` ищет по названию и домену, `status` фильтрует список. Сводка считается по всем проектам, а не по фильтру |
| POST | `/api/projects` | создать проект, этапы и событие. Ответ 201 |
| GET | `/api/projects/:id` | проект, этапы по порядку и история, новые события первыми |
| PATCH | `/api/projects/:id` | изменить название, домен, ТЗ, требования или режим. Статус, этап и прогресс через этот метод менять нельзя |
| DELETE | `/api/projects/:id` | удалить проект и зависимые строки. Ответ 204 |

SQL собирается только из фиксированных фрагментов. Значения пользователя передаются параметрами. Символы `%`, `_` и `\` в поиске экранируются.

## Будущие сервисы

Каталог в `backend/src/automation/registry.ts`:

| Сервис | Этапы | Сейчас |
| --- | --- | --- |
| `crawler` | сбор | в разработке, не выполняется |
| `analyzer` | паспорт | в разработке, не выполняется |
| `designer` | концепция | в разработке, не выполняется |
| `developer` | разработка | в разработке, не выполняется |
| `qa` | тестирование | в разработке, не выполняется |
| `publisher` | демоверсия и публикация | в разработке, не выполняется |
| ИИ-модели | — | не подключено |
| Внешние API | — | не подключено |

`startStage()` в `backend/src/automation/runner.ts` фиксирует границу запуска и всегда выбрасывает `AutomationNotReadyError`, не изменяя базу. Публичного маршрута запуска нет, чтобы интерфейс не обещал операцию, которой нет.

Когда сервис будет готов:

1. Добавить обработчик в `backend/src/automation/handlers/<service>.ts`.
2. Зарегистрировать его в каталоге и разрешить `startStage` вызывать только зарегистрированный обработчик.
3. В транзакции перевести этап в `in_progress`, пересчитать `progress` и `currentStage` через `deriveProgress` / `deriveCurrentStage`, записать событие.
4. Поставить работу в фон через `setImmediate` или `worker_threads`. Позже это место можно заменить очередью, не меняя HTTP-контракт.
5. Сразу вернуть клиенту 202 и идентификатор задачи. Сбор, анализ и генерация не должны находиться внутри времени запроса.
6. По завершении фоновая работа сама записывает `completed` или `error`, текст ошибки и событие истории. Для режима «Согласование этапов» перед следующим шагом ставить `awaiting_review` и ждать отдельного подтверждения.
7. Только после этого менять статус интеграции в каталоге на `ok`. До реальной настройки он не должен становиться «Подключено».

Панель читает статусы интеграций из `/api/health`, а не из захардкоженного списка, поэтому неподключённый компонент нельзя случайно показать как работающий.
